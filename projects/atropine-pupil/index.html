Case study

Note

Every chart on this page uses simulated data. No patient data, real estimates or real figures appear here.

The question

Atropine eye drops are used to slow myopia in children: the eye grows too long, and the drops slow that growth. They also dilate the pupil, as a side effect you can see without any special equipment.

So: can atropine-induced pupil dilation flag whether myopia treatment is working? If the children whose pupils dilate more are also the ones whose eyes grow more slowly, a pupil measurement could become a cheap, visible early sign of treatment response.

The data was a clinic’s export from an IOLMaster, a machine that measures the eye’s length (axial length) and pupil size at each visit. This page is about the reasoning more than the model. Most of the work was deciding what question the data could actually answer, and making sure the answer couldn’t be quietly steered.

What made it hard

The patient is the unit, not the eye

Each child contributes two eyes and many visits. Two eyes share genes, age, diet and how reliably the child takes their drops, and ten visits from one child are ten looks at one child, not ten pieces of independent evidence. Treating every row as independent would make the evidence look far stronger than it is.

So every model is a mixed-effects model with visits nested in eyes nested in patients: each patient and each eye gets its own baseline offset, and the model learns how alike they are. It also copes with the irregular, gappy follow-up that real clinics produce.

Two questions hiding in one variable

“Does more dilation go with slower growth?” can mean two different things:

  • Between eyes: are eyes that dilate a lot in general the ones that grow slowly? This is the question as asked, but it can be confounded: children who dilate more might be on a higher dose, take their drops more reliably, or have lighter irises.
  • Within an eye: when an eye is more dilated than its own usual, does it grow more slowly in that period? Each eye is compared only with itself, so fixed traits cancel out.

Put raw dilation into a model and you get a blend of the two that answers neither. The fix is to split it: each eye’s average dilation (between) and each visit’s deviation from that average (within).

def split_pupil(fu, col="pupil_change"):
    fu = fu.copy()
    # "A big dilator?" and "more dilated than usual at this visit?"
    fu["pupil_between"] = fu.groupby(EYE)[col].transform("mean")
    fu["pupil_within"] = fu[col] - fu["pupil_between"]
    return fu

function rng(seed) {
  let a = seed >>> 0;
  return () => {
    a = (a + 0x6d2b79f5) | 0;
    let t = Math.imul(a ^ (a >>> 15), 1 | a);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

function normal(r) {
  return Math.sqrt(-2 * Math.log(1 - r())) * Math.cos(2 * Math.PI * r());
}

function ols(xs, ys) {
  const mx = d3.mean(xs), my = d3.mean(ys);
  const slope = d3.sum(xs, (x, i) => (x - mx) * (ys[i] - my)) / d3.sum(xs, (x) => (x - mx) ** 2);
  return { slope, intercept: my - slope * mx };
}

The question as asked compares children, so the between-eye effect was the primary result and the within-eye effect secondary, with the confounding risk of the between comparison written into the plan’s limitations before anything was fitted.

No untreated group

Every child’s first visit is before atropine and every later visit is on it, so there’s no untreated comparison group. Each eye’s own pre-treatment visit is the only “before”.

To see what an untreated history might add, I ran a side experiment: a synthetic ghost baseline, inventing years of untreated growth before each eye’s first visit at typical untreated rates. It was useful and also showed its own limits. Because the invented growth was unrelated to pupil size, it could confirm the atropine effect I had built into it, but could never reveal a pupil–response link. It’s kept apart from the main analysis and labelled exploratory.

A messy export

The raw IOLMaster export needed real work before any analysis:

  • a file-version line above the column names;
  • test records mixed in with patients, and IDs that had to be checked one-to-one with patients;
  • repeat scans on the same day, some marked “Successful” and some only “Warning”;
  • eyes that appear to shrink between visits, usually a measurement or left/right label error;
  • pupil sizes taken under unrecorded lighting, so the exposure itself is noisy.

All of this is handled in code, never by hand in a spreadsheet: suspect rows are flagged, not deleted, so the main analysis keeps them and the sensitivity analyses test what happens without them.

trajectories = {
  const r = rng(42);
  const rows = [];
  for (let e = 0; e < 16; e++) {
    const base = 24 + 0.9 * normal(r);
    const rate = Math.max(0.03, 0.2 + 0.08 * normal(r));
    for (let t = 0; t <= 3.2; t += 0.35 + 0.4 * r()) {
      rows.push({ eye: e, years: t, AL: base + rate * t * (1 - 0.08 * t) + 0.015 * normal(r) });
    }
  }
  return rows;
}

Rigour

The pipeline runs in fixed phases, and each one feeds the next:

  • The plan was locked before any model was fitted. The question, outcome, exposure, adjustments, model and every sensitivity analysis were written down, dated and committed first. Any later change is logged with what changed and why, and anything decided after seeing results is labelled exploratory. Try ten analyses and report the one that “worked”, and the p-value means nothing.

  • Models were built up in steps: time alone, then age, starting eye length and sex, then the pupil terms. Watching coefficients move between steps shows what is explaining what.

    STEPS = {
    "1_time": "AL_rate ~ years",
    "2_background": f"AL_rate ~ years + {BACKGROUND}",
    "3_primary": f"AL_rate ~ years + {BACKGROUND} + {PUPIL}",
}

  • Diagnostics paid for themselves. Residual and leave-one-patient-out checks caught two things: one optimiser reporting convergence at a clearly worse solution (so each model is now fitted with two optimisers and the better fit kept, with both reported), and one “patient” who turned out to be a staff test scan. Both fixes went into the plan’s change log.

  • Sensitivity analyses, all reported: around a dozen pre-listed variations, including pupil measured at the start of each interval, a population-average GEE model, one eye per patient, different interval rules, dropping flagged scans, and a cluster bootstrap that resamples patients, not rows:

    def bootstrap_sample(fu, rng):
    rows = fu.groupby("Pat_ID").indices
    draws = rng.choice(list(rows), len(rows), replace=True)
    # Each copy of a patient becomes its own cluster
    parts = [fu.iloc[rows[p]].assign(Pat_ID=f"{p}#{k}")
             for k, p in enumerate(draws)]
    return pd.concat(parts)

  • Reported to the STROBE checklist, the standard for observational studies.

  • Test-driven throughout: about 120 tests cover cleaning, quality checks, features, models, sensitivity analyses and the report build, each written before the code it tests.

What it found

This was set up as an estimation study, not a hunt for p < 0.05: the aim was the size of the association and its confidence interval, read against how fast myopic eyes grow, so the answer is useful whichever way it goes.

Read that way, no clinically meaningful association was detected between how much a child’s pupils dilate and how fast their eyes grow on atropine. That’s a useful answer in itself: pupil dilation alone shouldn’t be read as a sign the treatment is working. Because the pupil measurements are noisy, it also doesn’t rule out a real but small link, which better measurement could test.

forestRows = {
  const r = rng(2026);
  const labels = [
    "Primary model",
    "Pupil at interval start",
    "Cumulative growth",
    "GEE (population average)",
    "Cluster bootstrap",
    "One eye per patient",
    "Other interval rules",
    "Season term",
    "Eyes with 3+ intervals",
    "Drop flagged intervals",
    "Drop Warning-only scans",
    "Child-level dilation",
    "Device software version"
  ];
  return labels.map((label, i) => {
    const est = 0.006 * normal(r), half = 0.015 + 0.012 * r();
    return { label, est, lo: est - half, hi: est + half, primary: i === 0 };
  });
}

Two audiences

The analysis produced two reports from the same results. The full technical report has the models, diagnostics, every sensitivity analysis and the STROBE checklist. A separate plain-language report, three pages at most, is for the clinicians: what was asked, what was found, what it does and doesn’t mean for their patients, and no statistical jargon. Both come out of one build command, so they can’t drift apart.
